# Cursor-Anchored Voice Input — Project Plan

Status: **rev 3** (gesture decided) · Branch: `feat/cursor-input-method` · 2026-11-02

Rev 1 was written from the README and a file listing. Rev 2 corrects it against
`docs/research/cursor-input-codebase-map.md`, which is the evidence base for every
claim below (file:line references live there). Where the two disagree, the map wins.

---

## 1. The idea in one sentence

Turn VocalCode from *"hold a shortcut, then speak"* into a **pointer-native input
method**: a small click-through dot follows the mouse cursor, arms when the pointer
is over an editable text target, and a gesture on that dot toggles dictation — no
keyboard chord, no separate invocation step.

## 2. Why this is worth building

Today: *click into the field → move hand to keyboard → press the talk key → speak.*
The trigger and the aim live in different input devices.

A cursor-anchored control collapses them, and — unlike a global shortcut — it can
refuse to arm where we could not legally deliver text anyway (elevated windows,
secure desktop). That makes it *safer* than a blind hotkey, not just faster.

## 3. Product spec (v0)

### 3.1 The dot

- Opt-in: `Cursor input mode`, **Settings → Dictation**, off by default.
- A ~10 logical-px dot, offset below-right of the pointer, following it.
- **Visible whenever the mode is on** (decision D2), in every state — a dot that
  appears from nowhere is more startling than one that changes colour. It is the
  affordance that tells you the feature exists.
- **Click-through, always.** It never takes focus and never receives a click. Its
  only job is feedback; the gesture lives on the field (§3.2).

| State | Meaning | Look |
| --- | --- | --- |
| `Idle` | pointer not over an editable target | dim dot |
| `Armed` | pointer over a target we would accept text in | accent ring |
| `Listening` | capturing | dot morphs into a small live waveform |
| `Transcribing` | audio closed, waiting for text | slow pulse |
| `Delivering` | injecting | brief fill |
| `Blocked` | elevated / secure / fullscreen target | hidden |

### 3.2 The toggle gesture

**Decided (D1): double-click on the editable field.** Two `WM_LBUTTONDOWN` events
inside `GetDoubleClickTime()` while the pointer is `Armed` start dictation; the next
double-click sends `ForceStop` and injects.

**The constraint this accepts.** `WM_LBUTTONDBLCLK` is generated by the target
window's own class and never reaches our low-level hook. The click is therefore
delivered to the application *before* we can act on it, and the application will
word-select. There is no way to prevent that short of swallowing the first click for
up to 500 ms, which would delay every click in the system.

Consequences, accepted deliberately:

1. **In an editor, double-click stops selecting a word** while cursor mode is on.
   This is the price of the gesture. Mitigations: the mode is off by default, it has
   a one-click toggle in the tray, and `Shift`+double-click is left to the
   application as an escape hatch.
2. **A word will be selected when dictation starts.** If we do nothing, the injected
   text *replaces* that word. So the controller must **collapse the selection before
   delivering**: query `TextPattern.GetSelection()`; if the range is non-degenerate,
   send `VK_RIGHT` to collapse it to its right edge, then type. Text is then appended
   after the double-clicked word, which is what "dictate here" means.
   Where no `TextPattern` is available, fall back to a single `VK_RIGHT`.

**The stop half is not symmetric.** A second `HandsFreeStart` is a no-op while
recording (`engine.rs:861-864`), so stopping must be an explicit `ForceStop` through
the controller's own `Bridge`.

**Arming is the safety gate.** A double-click only counts as a toggle when the point
is over a target the probe says is editable. Double-clicking the desktop, the
taskbar, a game, or an elevated window does nothing.

### 3.3 "Recognising the current input"

Two separate problems, only the first is new:

1. **Target detection** — is the point under the pointer editable? Drives `Armed`.
   Must fail closed: no arm → no dot → no surprise typing.
2. **Speech recognition** — already solved; unchanged.

### 3.4 Delivery

Reuse the existing injector and its guards. Text lands at the caret of the target
that was armed when dictation started.

## 4. What actually exists

| Need | Reality |
| --- | --- |
| Global mouse hook | **Already installed**, both `WH_KEYBOARD_LL` and `WH_MOUSE_LL` (`hook_windows.rs:279-288`). `mouse_proc` already holds `MSLLHOOKSTRUCT`, including `pt` and `time` — it simply never reads them (`:188`). |
| Pointer position | **Free.** Store `(pt.x, pt.y)` in a `static AtomicU64` inside `mouse_proc`, before dispatch. No second hook, no thread, no lock. Motion is currently filtered out at `:17-19`; the capture belongs *above* that filter. |
| Click edges with time | **Free.** `MSLLHOOKSTRUCT` carries `time`; button edges already reach the handler. Clicking can be counted without consuming the event. |
| Editable-target predicate | **Exists, for the focused element only** — `inject.rs:527-557` (password check, read-only `ValuePattern`, Edit/Document, `TextPattern`). The *point-based* variant (`ElementFromPoint`) does not exist. |
| Text delivery + guards | Mature: `FocusToken`, focus re-validation per chunk, clipboard fallback on `Diverted`. Reuse as-is. |
| Dictation lifecycle | `Engine::handle` (`engine.rs:858`), driven from `main.rs:5010-5234`. Programmatic control goes through `dictation_control::Bridge`, consulted at `main.rs:4990-5009`. |
| Floating surface | Two exist. `control_bar.rs` has per-frame `SetWindowPos`, cadence control, arbitrary sizes and JSON payloads; `overlay.rs` has the click-through styling. **Take geometry from the former, styling from the latter.** |
| Config | TOML v5, additive tables already the documented reversible pattern. |

**Honest completion estimate: ~50%, not 70%.** Delivery and settings are done. The
four things the feature *is* — pointer tracking, point-based UIA probing, per-frame
window positioning, click policy — are all at zero.

Three rev-1 errors worth recording:

1. `workflows.rs` is **not** the dictation lifecycle; it stores per-app cleanup
   preferences.
2. The vendored `rdev` does **not** carry coordinates on `ButtonPress`, and it is
   not even the Windows input path (`hotkey.rs:1020-1074`). VocalCode's own hook is.
3. There is **no positioning IPC** and **no platform timer thread**. Rev 1 invented
   both.

## 5. Architecture

### 5.1 New code

**`vocalcode-platform/src/pointer.rs`** (or an extension of `hook_windows.rs`)
- `MOUSE_POSITION: AtomicU64` written from `mouse_proc` for moves *and* button edges.
- `cursor_position() -> Option<(i32, i32)>` — physical screen coordinates.
- `text_target_at_point(x, y) -> Option<TextTarget>` — `IUIAutomation::ElementFromPoint`
  plus the existing gates from `inject.rs:534-556`.

Rules for that probe, learned the hard way from the existing code:
- cache `IUIAutomation` in a thread-local; `CoCreateInstance` per call is too slow;
- run it on a worker with a hard timeout and a generation token — a hung provider
  must never block the hook thread or the UI loop;
- keep last-known-good state so a slow probe does not flicker the dot.

**`vocalcode-app/src/cursor_dot.rs`**
- Copy `control_bar.rs`'s `Bounds` / `SetWindowPos` / `next_wake` / JSON-payload
  machinery; take `overlay.rs:388-402`'s `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE |
  WS_EX_TOOLWINDOW`.
- A `CursorVisual` enum of its own — **do not extend `Phase`**, which is a 3-bit
  field that also gates control permissions.
- Injectable cursor source (`Fn() -> (i32, i32)`) so positioning arithmetic is
  unit-testable.

**`vocalcode-app/src/cursor_input.rs`**
- The state machine, arming hysteresis, and the double-click policy
  (`GetDoubleClickTime()` + `SM_CXDOUBLECLK`/`SM_CYDOUBLECLK` tolerance; no state
  for this exists in the tree yet).
- **Selection collapse before delivery** — §3.2 consequence 2. This is not optional:
  without it the first dictation after a double-click overwrites the word the user
  double-clicked.
- **Its own `Bridge`** — the existing one is a single-slot mailbox with a 750 ms TTL
  and a busy latch; sharing it with the control bar makes them reject each other.
- Consulted next to `status.dictation_control.take(...)` in `main.rs:4990-5009`.

### 5.2 Changes to existing code

- **`main.rs:4997`** — the gate is literally `active_config.desktop_control`. Widen
  it to `desktop_control || cursor_input.enabled`, or the bridge refuses every start.
- **`webui.rs`** — apply the dot's `next_wake` beside the control bar's
  (`:1861-1863`), and only while the pointer actually moved.
- **`config.rs`** — add a `[cursor_input]` table, **last** in `Config`, following the
  `[writing]` pattern. **Do not bump `CONFIG_VERSION`**: a bump to 6 makes today's v5
  builds refuse the user's data folder. Additive + `#[serde(default)]` is reversible
  by design and has a test proving it.
- **`webui.html`** — one toggle + one dropdown, following the `desktop_control`
  pattern; translations needed in all five languages.

### 5.3 Threading

| Concern | Thread |
| --- | --- |
| Pointer capture | hook callback (already runs on every mouse event) |
| UIA point probe | dedicated worker + timeout + generation token |
| Dot reposition | UI loop, woken at ~33 ms via `next_wake` while active |
| Dictation start/stop | engine thread, via its own `Bridge` |

## 7. Risks

1. **Double-click collision** — see §3.2. Accepted by design: in an editor,
   double-click stops selecting a word while the mode is on, and the selected word
   must be collapsed before delivery or the first dictation overwrites it.
   This is the single most likely source of user complaints; it needs a visible
   escape hatch (tray toggle, `Shift`+double-click passthrough).
2. **UIA hangs** — the current code has no Windows timeout and creates COM per call.
   A probe on the UI thread would freeze the app on a busy provider. Worker + timeout
   is mandatory, not an optimisation.
3. **Elevation / UIPI** — `foreground_application()` returns `None` when
   `OpenProcess` fails, which is the normal outcome for a higher-integrity
   foreground process. Use that as the `Blocked` signal; do not add an elevation API.
4. **Fullscreen** — `foreground_is_fullscreen` already exists and is reusable.
5. **Secure desktop / lock screen** — hooks are per-desktop and simply go silent.
   Treat "no input + no foreground window" as `Blocked`; no helper exists yet.
6. **DPI crossings** — Windows sends `WM_DPICHANGED` and tao resizes; a fixed-size
   dot must re-assert its size every frame or it drifts.
7. **Config version** — do not bump. (See §5.2.)
8. **Branding / licence** — AGPL-3.0-only; a redistributed fork must not present as
   upstream. See `BRANDING.md`.

## 8. Verification

- `--build-info` identity check.
- Unit tests for positioning arithmetic with an injected cursor source (mirroring the
  `bottom_centre_in_work_area` tests).
- `cursor_dot_hidden_smoke`: asserts `IsWindowVisible == 0`, the extended styles, that
  `GetForegroundWindow()` is unchanged, and computed positions across a grid of
  points including negative coordinates and 100/150/200% monitors.
- One `#[ignore]`d live probe for real hook + UIA behaviour, in the style of
  `keyboard_capture_live.rs`.
- Manual matrix: Notepad, Word, VS Code, Chrome `<input>`, Chrome `contenteditable`,
  Terminal, Explorer rename, elevated Notepad, fullscreen game, multi-monitor DPI
  change.

## 9. Non-goals for v0

- No ASR/model changes, no cloud, no meeting-feature changes.
- Not a replacement for the hotkey.
- No per-app configuration.
